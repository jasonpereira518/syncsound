| 1 | TypeScript 6.0.x | TS 7 (native) | typescript-eslint 8.x peer range is `<6.1`. |
| 2 | Packages export `.ts` source, no build step | tsup/tsc builds per package | Fewer moving parts; Next `transpilePackages`, `tsx` for server, Vitest native TS. |
| 3 | Plain Node `http` + `ws` server | Bun, uWebSockets.js | `ws` is the prompt's default; runs everywhere incl. CI/Docker. |

| 5 | `apps/web/tsconfig.json` maps `zustand/vanilla` + `zustand/react` via `paths` | rename the checkout dir | TypeScript substitutes `*` of package `exports` patterns into the *whole* absolute path, and this checkout lives under `**Quick Projects`. The mapping is harmless in any other path. |
| 6 | Snap every `AudioBufferSourceNode.start(when, offset)` to the sample grid (`snapToSampleGrid`) | keep sub-sample starts | Chromium linearly interpolates fractional-sample starts → up to −2.4 dB at 11 kHz (found by the loopback-calibration E2E: a "flat" loopback measured 2.7 dB droop; 0.00 dB after the fix). Timing error ≤ 10 µs. |
| 7 | `?loopbackMic=<ms>` test mode records the device's own calibration emissions instead of the mic | fake-mic WAV (can't be time-aligned) | Lets Playwright run the full calibration wizard + real measurement code in a real browser. |
| 8 | Web store split into `store/state.ts` (zustand) + `store/roomStore.ts` (actions) | one file | lib modules write to the store without an import cycle. |
| 9 | Host auto-sends `defaultObjectsFor(channels, upmix)` per (track, channels, upmix), keeping existing positions | manual object setup | 5.1 files would otherwise be half-silent with the default L/R scene. |
| 10 | Spotify PKCE via popup (falls back to full redirect) | redirect only | Keeps the room page (and its AudioContext) alive during sign-in. |
| 11 | `expectedHeardEpochMs = timeOrigin + ctxToPerf(when) + L − (offset − trackOffset)·1000` | brief's formula | The brief double-counted auto latency in fallback mode; unit test checks devices with different latencies agree. |
| 12 | Sync-measurement tool: all devices emit device-unique chirps simultaneously once per second (`purpose: 'measure'`, slot `repeat`/`periodMs`), listener separates by matched filter, error = arrival − per-click mean | per-device sequential clicks | One recording measures true simultaneous sync; listener input latency and clock error cancel. Emitters use FULL playback compensation with a 1.5 s lookahead so the measurement reflects real playback. |
| 13 | `AudioClockMap` detects output-path latency steps (3 consecutive outliers > 6 ms agreeing within 3 ms) and shifts history onto the new regime | fixed regression window | A 44 ms output-latency step (seen in Chromium when a recorder starts; also Bluetooth profile switches) bent the regression into a −11 000 ppm slope for 16 s → clicks 30 ms off. Found by the loopback sync-measurement E2E (jitter 9.5 ms → 0.03 ms). |
| 14 | Recorder writes zeros for blocks where its input is inactive; calibration waits 1.5 s after opening the input before scheduling | — | Keeps sample index ↔ context time exact; lets the output path settle after opening a mic. |
| 15 | `?fakeCapture=tone|silent` test hook replaces getDisplayMedia with a synthetic stream | skip capture E2E | Exercises the real WebRTC mesh, receive path and DRM-silence detection headlessly. |
| 16 | Capture transport = plain RTCPeerConnection mesh (host → each device) | LiveKit SFU | No extra infrastructure; fine for small rooms (host uplink = N × ~256 kbps Opus). LiveKit recommended beyond ~8 devices (see LIMITATIONS). |
| 17 | Room UI is a fixed-viewport shell: header · Library (queue + sources) \| Stage \| Devices/Calibrate tabs · bottom player bar (Spotify layout); panes scroll internally, the page never does. Phones: one pane at a time via the bottom tab bar, player bar above it. Stage rendering/room-size settings fold into a `<details>` | long dashboard page | Everything (incl. transport) visible at once on desktop; the stage map keeps the height. |
| 18 | R1: drift control is a critically damped PI loop (Kp = 1/4 s, Ki = Kp²/4), no deadband; the integral (learned clock-rate mismatch) persists across tracks and is forgotten on output-route change | feed-forward from `AudioClockMap` slope | Self-contained in `DriftController` and needs no new plumbing. A deadband turns the integral into a limit cycle. Sim mean bias 1.48 → 0.12 ms. |
| 19 | R1: LAN clock master. Peers sync to one in-room device's raw `performance.now()` over an unordered, no-retransmit DataChannel at 10 Hz (128-sample window), and the master shares its server `ClockSync` mapping (`ClockMapping`) every 500 ms. Election: connected host, else desktop/laptop, else lowest id. | Peers sync to the master's *room-time estimate* | That estimate slews, and peers lag it (sim p95 0.95 ms). Sharing the mapping makes the WAN error identical on every device (sim p95 0.41 ms). Server clock stays the fallback whenever the link isn't ready. |
| 20 | R1: `RTC_SIGNAL` gains an optional `ch: 'capture' \| 'clock'` | A second message type | Additive; capture signaling is unchanged when `ch` is absent. |
| 21 | R1: `outputLatency` > 120 ms classifies the output as Bluetooth (in addition to the label regex) | Label only | Browsers don't expose the route, but wired/built-in outputs report ≲ 60 ms. Bluetooth jitter measurement and quick re-sync move to R3 because they extend the calibration code. |
| 22 | R2: the device `role` *is* its layout slot (L R C SL SR RL RR Sub, Full = unassigned); `scene.layout` (optional, absent = custom) picks routed vs positional mixing | Separate slot map in the scene | Role already exists, is per-device and persisted in profiles; one field instead of three disagreeing ones (role dropdown, join-order presets, objects). |
| 23 | R2: routed layouts reuse the object pipeline: `computeDeviceMix` swaps DBAP for `routedGains` (equal-power within a slot, fold-down chain C→L/R, SL→RL→L, AMB→surrounds→fronts); unassigned devices are silent there | A new channel-matrix render path in the engine | Zero engine/graph changes; bass management, EQ, delays and calibration all keep working unchanged. |
| 24 | R2: `autoAssign` fills slots by device class (desktop > laptop > bluetooth > tablet > phone, then join time) and keeps existing subs; the role dropdown stays until R5's room diagram replaces it | Auto-pick subwoofers by `bassCapable` | Promoting a laptop to "sub" would be a surprise; subs are a user choice. The dropdown now really moves sound, so it stays useful until the diagram lands. |
| 25 | *(Superseded by #56.)* R3: loudness still matches the quietest device (equal dB is guaranteed); devices > 3 dB under the median get `volumeUpDb`, shown on that device as "turn this device up, then re-tune" | Median target with up to +6 dB software boost (the plan's first idea) | The output limiter sits at −3 dBFS, so a boost compresses or clips loud material. Raising the hardware volume and re-tuning gets the same loudness cleanly. |
| 26 | R3: "Quick re-sync" = the normal calibration with chirps only (`include: ['chirp']`), ~1.1 s per device; it sends only latency (no trim/EQ/volumeUp fields) | A single-device re-measure | Relative latency needs every device's arrival as a reference; chirp-only keeps one code path. Sim: same < 1 ms accuracy as the full pass. |
| 27 | R3: calibration pauses playback when this device may control it and resumes the same track afterwards; `volume` joins `PROFILE_KEYS` | — | Music under the sweep ruins the measurement; a device's volume should survive a rejoin like its trim does. |
| 28 | R4: persistent Home: `HomeStore` (`${dataDir}/homes.json`, same debounced JSON pattern as profiles via a shared `JsonStore`) holds `{ id, ownerKeyHash, rooms[] }`. No accounts: the home id is a capability link; the 128-bit owner key is stored as a SHA-256 (no salt/KDF needed at that entropy) and doubles as JOIN `hostKey` in home rooms. Stored room ids are room codes in the same code space as temporary rooms, so JOIN-by-code and old `/room/[code]` links work unchanged; `RoomManager.get` brings a stored room up on demand, the TTL sweep only unloads it, and `Room` writes scene/settings/password hash back through `onConfig`. Home rooms keep pruned speakers' positions. Home API is HTTP (`/api/homes…`, owner key in `x-owner-key`), not WS `HOME_*` messages | WS `HOME_*` messages | A joined socket drops anything not room-sequenced (`seq ≤ lastSeq`), and the home page joins no room. Group play = one start time `T = now + max(room lead)` applied to every room via `Room.controlAt`, so all SCHEDULEs share `startRoomTime` on the shared perfClock. |
| 29 | R5: one room page with four views instead of new routes. Setup wizard (a host's first visit, until a layout exists), Now Playing (controllers), speaker screen (guests), and Advanced (the previous full shell, `#advanced`) | `/room/[code]/advanced` as its own route | Switching views keeps the joined session and AudioContext alive; a route change would unmount and leave the room. |
| 30 | R5: Home flow is landing "Set up my home" (creates a home plus a "Living room"), then `/h/[homeId]` (rooms, live speaker counts, add/rename/remove for the owner), then open a room. The owner key is copied into each room's host-key slot so the owner joins as host. Quick unsaved rooms stay as a secondary action | Accounts | Matches R4's capability-link design; no sign-up step. |
| 31 | R5: the layout logic moves to store actions (`setLayout`, `assignSlot`) used by both the wizard and the Advanced stage. Speakers are named by slot ("Front left"), and the room diagram (slots around the seat) is the single place to place speakers in the simple view | Keep the free-placement map for everyone | Tapping a labelled spot is understandable without knowing what DBAP is; free placement stays in Advanced. |
| 32 | R6: Advanced = the existing three-pane shell unchanged. The debug drawer (and its `D` shortcut) only mounts there, and everyone can open it, because it holds per-device latency/EQ fine-tuning; its controls still enforce host-only permissions | Host-only Advanced | A guest with a Bluetooth speaker may need the manual latency slider. |
| 33 | R5: Spotify/Apple Music sources are hidden when this deployment isn't configured for them (no developer setup text shown to users); source chips are renamed by what they are ("Music file", "Browser tab", "Spotify (sync only)") | Show setup instructions | End users can't act on `NEXT_PUBLIC_…` instructions. |
| 34 | Gap pass: `GET /api/rooms/:code` returns the room's `name` for home rooms (never the home id); the page title, header and join screen use it, and the last joined room is remembered for a "Rejoin <name>" button on the landing page | Put the name in `RoomState` | The join screen needs the name before joining; one optional field on an existing response. Room codes are shared with guests, home links aren't. |
| 35 | *(Superseded by #55.)* Gap pass: after a full tuning pass with a Bluetooth speaker present, a 10 s sync measurement runs automatically and its per-device std is shown as "Bluetooth timing varies by ±X ms". Sync measurement now pauses/resumes playback like calibration | Extra chirps inside the calibration plan | Reuses the measurement tool already proven in sim and e2e; no new analysis code. |
| 36 | Gap pass: an `AudioClockMap` output-latency step (outside a measurement and its 5 s tail) raises the same "re-sync" banner as a route change, now with a "Re-sync now" button (quick re-sync) | Silent re-sync | A re-sync needs the mic and quiet, so the user starts it; the banner tells them why. |
| 37 | Gap pass: group play is in Now Playing (owner, home rooms): pick other rooms, then queue the current track there and send one `play` to all of them through the home group API | A separate home-level player | The track and position already live in the room the owner is using. |
| 38 | Landing: theme "Listening room" (warm near-black ground #0e0c0a, bone ink #eeeae3, one amber accent #ffb23e, Chillax self-hosted) applied by remapping the existing `ink-*`/`accent` tokens, so home and room screens change with no class edits; `warn` moves to #e9d96a to stay apart from amber, `role-*` data colours unchanged | A landing-only palette | Chosen with the user; one theme for the whole site. |
| 39 | Landing: speaker pictures are offline three.js renders (`pnpm render:speakers`, headless Chromium via Playwright → WebP), cabinet and woofer cone as separate transparent layers so CSS pumps the cone around its real centre (`renders.json`). `three` is a root devDependency only | Real-time 3D in the page; AI-generated photos | Photoreal look with no 3D code shipped (~320 KB for all eight stills); exact, repeatable geometry for the pump. | 40 | Landing: the live demo uses the real `slotPositions` + `dbapGains` on `defaultScene()`; the "How it works" ritual is a range input, not scroll-driven; section reveals are a one-shot IntersectionObserver under `html.js` + no-preference motion | Scroll-timeline (`view()`) reveals | Content never depends on scroll or script to be visible; the taste inspector measures hidden view-timeline elements as blank page. |
| 41 | Calibration chirp search window is `[slot − 400 ms, slot + maxLatency + 1500 ms]` (was −100/+600) and out-of-nominal arrivals are flagged, not dropped; `scanArrival` returns the best match without gates and `analyzeCalibration` exposes `bestPeak/bestSnrDb/arrivalOffsetMs/recordingPeakDb`; failures say *why* (mic silent / too weak / too noisy), the failed mic recording can be saved as .wav, and a 2 s self-test (own chirp, mid band) runs before the real plan | keep the fixed window + one generic error | "No speakers were heard" covered mic silence, speaker not emitting, arrival outside the window and weak signal alike. Sim: arrivals at −150 / +700 ms were missed. The real-mic path is only exercised by hardware, so the failure must be self-diagnosing. Devices that aren't running/clock-synced no longer emit (`onPlan`) instead of playing ~1.5 s early. |
| 42 | Schedule lead = max over connected devices of (RTT + max(0, manual + calibrated + browser-reported latency)) + safety margin, output part clamped to 2 s (`minScheduleLeadMs`) | RTT-only lead | A Bluetooth device starts its source ~100–300 ms before the room time; with an RTT-only lead it got the SCHEDULE too late, started "late" and skipped the start of every play/seek. |
| 43 | Manual latency range ±1000 ms (`MAX_MANUAL_LATENCY_MS`) | ±500 ms | Some Bluetooth speakers exceed 500 ms; matches the calibrated-offset range. |
| 44 | Calibration listener avoids Bluetooth: switches from a Bluetooth headset mic to a non-Bluetooth input, refuses if only Bluetooth mics exist, and leaves its own output out of the run when that output is Bluetooth/headphones (warning shown) | measure everything | Opening the mic flips Bluetooth into its hands-free profile (different latency, call quality) and a headset mic records at the speaker, so the listener's own Bluetooth measurement would be wrong. |
| 45 | Per-output calibration memory in localStorage keyed by the browser's output label; on devicechange: same label → nothing, known label → restore, new label → clear calibratedLatencyMs + prompt, no label → prompt | server-side per-output profiles | Labels are browser-local and only readable with mic permission; the client is the only place that knows them. Clearing on a new output avoids keeping a Bluetooth offset on the built-in speaker. |
| 46 | Calibration v3 timing comes from the listener's own recording: `cal_i = M(L,i) − |p_i − mic|/c − min` | Two-way ε/λ table solved by median polish over every recorder | `propagationDelays()` adds the same distances back, so arrivals at the mic align whatever the distance error; a table would carry every geometry-model error (speaker–mic prior, chassis conduction, L/R first-arrival flip, embedding residual) into timing and has no redundancy for N ≤ 3. |
| 47 | Every device with a mic records the tune; distances by two-way ranging (BeepBeep), used for positions only | Single listener + hand-dragged positions; multilateration | One mic can't separate latency from distance. BeepBeep cancels every clock offset and latency. Measured positions feed DBAP and the mic→head correction. |
| 48 | *(Superseded by #57.)* One 0.7 s Farina sweep (20 Hz–20 kHz, −12 dBFS; response grid 20 Hz–16 kHz) per device replaces chirp + sweep + pink noise; arrival = earliest envelope peak within 5 ms before the strongest, ≥ −12 dB, in a 1–12 kHz band | Narrow-band device-unique chirps (envelope ~10 ms wide) | Wideband → sub-ms, reflection-resolving peak; one signal gives timing, level and response. Identical sweeps need non-overlapping search windows: slot period 1.55 s covers −0.4…+1.0 s of arrival offset (AirPlay-class ~2 s outputs aren't supported). |
| 49 | Listener head = tuning laptop's mic + 0.4 m behind it (azimuth 180°), adjustable/draggable | Align at the mic | A laptop mic sits ~0.4 m in front of the head; ignoring it costs up to ~1.4 ms off-axis. |
| 50 | Re-tune is never automatic: a clock-path change (LAN master ↔ server clock) sets the existing route-changed banner with one-tap Quick tune | Silent automatic re-tune | Automatic re-tunes would pause music and open a mic unattended, and the listener may not be at the spot. |
| 51 | A successful full tune resets the device's manual latency nudge to 0 | Keep the nudge | The nudge compensated exactly what the tune now measures; keeping it would double-count. |
| 52 | Sync check = staggered short wideband chirps (device i at i·250 ms), scored with the same first-arrival estimator, played through the output chain (limiter, delay, gain) | Simultaneous device-unique narrow-band chirps | Narrow-band chirps can't resolve sub-ms; the check must measure what playback does. |
| 53 | A device is excluded from ranging when it reports a Bluetooth output (recorder rows / caps); the direct-level co-location test is only a fallback | Level test alone | In sim a stereo laptop's direct sound is two half-amplitude arrivals, which hid a Bluetooth speaker 3.8 m from its laptop by 3 dB; the device itself knows its output. |
| 54 | LAN clock filter unchanged (window 128, best quarter) | Window 256 / best 15 % (p95 0.41 → 0.37 ms in lanMaster sim) | The gain is small and a longer window follows Wi-Fi path changes more slowly; the tune budget holds with the current filter. |
| 55 | A tune plays exactly one sound per device: the automatic 10 s Bluetooth sync measurement after a full tune is gone; the "±X ms" wobble line shows only after a manual sync check | Keep the auto check | Users heard a tune as a single pass; ten more seconds of clicks read as "it plays more than one sound". The measurement is unchanged and one tap away. |
| 56 | Loudness meets in the middle: trims bring every device to the median (cut loud, boost soft ≤ +6 dB, floor −24), the trim moved BEFORE the output limiter (`DeviceMix.trimGain`, volume after it); `volumeUpDb` = what the boost leaves short (> 1 dB) | Cut to the quietest (#25) | Cutting to the quietest made one soft device (or a misread one) turn everyone down. With the trim ahead of the −3 dB / 20:1 limiter a +6 dB boost compresses peaks instead of clipping (ceiling ≈ −0.8 dBFS incl. makeup gain). |
| 57 | Tune signal `'tune'`: 0.6 s sweep (20 Hz–20 kHz, top tapered −10 dB above 14 kHz, 30 ms fade-in) landing on a 0.5 s C6/G6 bell chime; arrivals matched against the swoosh only; response by a regularized inverse of the whole signal; slot stays 1.55 s; `'sweep'` kept in the protocol for older plans | Keep the plain Farina sweep; a pure chime (no EQ); a 2 s slot | The plain sweep sounded harsh. A pure chime can't measure the response. The Farina inverse turns the chime into tones in the IR window (+18 dB bumps). A 2 s slot let recorder rate error grow between slots (sim distance max 0.144 → 0.150 m vs a 0.15 m bound); a late device's segment overlapping the next (identical) signal deconvolves a whole slot away instead. Old tabs reject a `'tune'` plan (fail loudly, never mis-measure). |
| 58 | Level = K-weighted power mean 200 Hz–8 kHz (`loudnessDb`); the loudness median excludes the listener when ≥ 2 others have levels | 300 Hz–3 kHz dB mean; measure the listener's own speaker→mic distance from pair levels | The ear hears power, presence and treble, not a midrange dB average. The listener's own level rests on the 0.1 m near-field prior (a down-firing laptop speaker reads ~8 dB low), so it no longer sets anyone else's trim (sim: 0.0 dB shift with an 8 dB misread). Estimating the distance from pair levels needs a stereo-aware direct level (±3 dB bias) and would add error where the prior is right; logged in LIMITATIONS. |
| 59 | Auto-advance is server-driven: the ws adapter keeps one timer per room, re-armed after every delivery from `Room.nextDueAt()` (= next start − lead − 300 ms), and calls `Room.tick(now)`, which issues an ordinary `(startRoomTime = end of the current track, trackOffset 0)` SCHEDULE for the next track, or a `stop` 100 ms past the last track's end. A late tick starts at now + lead and shortens the crossfade instead of moving the start earlier | Clients advancing on their own at `onended`; a 1 s server poll | Room state stays authoritative (late joiners, Now Playing, group play all read it); per-client advances would drift apart and leave the server on the old track. The timer lives in the transport so `room.ts` stays portable; a timer beats a poll because the start must carry the full lead. |
| 60 | Crossfade is a room setting (`settings.crossfadeSec`, 0–12 s, default 0 = gapless) applied only at natural track ends. The applied value travels on the SCHEDULE / `playback.crossfadeSec` (clamped to half of either track, 0 into a sync-only track); each device fades locally with equal-power sin/cos curves from its *actual* start to the old track's end on the room timeline, and a 0 s join starts the new voice at full level (no 15 ms fade-in) while the old buffer ends on its own | Crossfade on manual skips too (Spotify does); fade lengths decided per device | A skip is a command and the 15 ms cut is its immediate feedback. Carrying the end on the schedule lets a late-starting device shorten its fade rather than overrun. The half-track clamp keeps a short track's fade-in finished before its fade-out starts (Web Audio can't edit automation inside a running curve). Carrying it in `Playback` also makes the UI's early title switch explainable (LIMITATIONS). |
| 61 | Re-queueing a known track only fills in a missing `durationSec` / `channels`; devices report what they decoded through the existing `queue` command (when control allows), so web links learn their length from the first decode | A new TRACK_UPDATE message; host-only reporting | Smallest protocol change that lets links auto-advance; `maybeAutoObjects` gets the channel count of a link for free. |
| 62 | Live-capture alignment delay is governed: getStats polled every 500 ms, median of 5, applied only when it moves ≥ 10 ms (or a slider moved), snapped to whole samples, and switched as a 10 ms dip → step → 10 ms rise on a gain after the DelayNode; a receiver stays silent until its first estimate | Glide with `setTargetAtTime` on every poll (previous); two crossfaded DelayNodes | `delayTime` is a-rate while automated: a glide is a pitch bend, every second, on every device (the "warble"), and a fractional delay is linearly interpolated (−2.5 dB at 11 kHz). Crossfading two delays sums two copies Δ apart (a flam/comb) on every switch. The dip sits after the limiter, so it never pumps. |
| 63 | Receiver jitter-buffer target = videoBufferMs / 2 (40–500 ms); `contentHint = 'music'` on the captured track | Fixed 40 ms (previous) | 40 ms is a speech setting: on Wi-Fi NetEq time-stretches and conceals to hold it, audible on music, and every adjustment feeds the delay estimate. Jitter belongs in the jitter buffer, which can conceal, not in the DelayNode, which can't; the other half of the buffer stays for alignment and output latency. |
| 64 | In-app YouTube player removed: YouTube plays in its own tab and is shared like any tab (two steps). The app tab is excluded from the share picker (`selfBrowserSurface`/`surfaceSwitching: 'exclude'`); the host monitors only a shared *tab* (`displaySurface === 'browser'`), never a window or the whole screen; a Capture Handle tags SyncSound tabs as a second check | Keep the embedded player with a silent host; let the host play the original undelayed | Capturing the app's own tab put the host's delayed monitor inside the stream: an echo every `videoBufferMs`, held up by the limiter, with the host silent. Excluding the tab makes the loop impossible rather than detected. A window or screen share is heard from the OS already; monitoring would double it and, with system audio, loop. |
| 65 | Server: `CAPTURE active` requires `canControl`, pauses a playing track (the pause math), and `play` is refused with `capture_active` while a connected device shares; the capturer forces a stereo scene | Let a file track and the live stream mix | The output chain's alignment delay would shift the file track by a different amount on every device, breaking its sync, and the two sources would simply mix. A leftover mono or 5.1 scene maps no L/R channel of the 2-channel live voice and mutes it. |
| 66 | E2E `?tap=1`: analysers on each device's output and on the live source, read through `window.__syncsound.tap()`; `liveDelay()` exposes the governor | Trust the receiving/peer flags (previous) | The old test never heard the received audio. The taps assert level, steadiness (6 dB envelope), both tones, stereo on the source, and that the delay is sample-exact and not re-switched while listening. |
